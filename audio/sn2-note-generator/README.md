# SN2 Note Generator

A Python script for a **two-synth, two-port rig**: a Novation Supernova II (8 Parts, its own MIDI OUT/DIN port) and a Korg microKORG XL (its own separate USB-MIDI "SOUND" port), each getting their own generative notes, mod wheel, wandering runs, preset cycling, and sound-design drift — plus a virtual fan-out port so a visualizer can watch everything in perfect sync, and built-in recording so every session is captured to a multi-track MIDI file automatically. A self-playing chaos generator.

**This is the single authoritative copy of the script.** It replaced an earlier divergent copy that (incorrectly) tried to reach the Korg by sending data on "channel 9" of the Supernova's own port — that channel never reaches the Korg's sound engine at all, since it's physically a different USB-MIDI port. See the 2026-08-18 consolidation changelog entry below for the full story.

## Files in this project

- **`sn2_chaos8_runs.py`** — the main script, described in this whole README. Runs are "global": one run happens at a time anywhere in the system, cycling between the 8 Supernova Parts and the Korg, with a long modulated pause (10-45s) between them.
- **`sn2_perpatch_runs.py`** — a variant with everything else identical (same routing, presets, modulation, sound-design CCs, crash-safety, fan-out, recording), but a completely different RUN system: each of the 8 Supernova Parts and the Korg gets its own independent run scheduler, firing a run roughly every 25-35 seconds, so runs on different patches can overlap and trade off with each other instead of taking turns one at a time. See "Per-patch runs variant" below for the details.
- **`sn2_recorder.py`** — shared recording helper imported by both scripts above (not run directly, except as the standalone log-to-.mid tool described in "Recording" below).

The two run scripts are kept side by side so Bill can pick whichever run behavior he prefers on a given night — pick one, run it, the other stays untouched.

## What it does

- Plays random notes on the Supernova's 8 Parts (channels 1–8, sent to its own MIDI OUT/DIN port) **and** the Korg (sent to its own separate "SOUND" USB-MIDI port) — nonstop, each voice with its own density/velocity/activity modulation on its own phase offset so nothing moves in lockstep.
- Every so often, moves the mod wheel on each of the 8 Supernova channels to a random position, independently of the notes.
- On top of that background chaos, one "run" happens at a time: a short wandering melody of 5 or 7 notes, played back-to-back on a randomly chosen target — any of the Supernova's 8 Parts, or the Korg (1-in-9 chance each, same weight). While a run is playing, that voice's random notes pause so the run stands out. After a run finishes there's a 10–45 second pause before the next one starts (possibly on a different target). Each run's shape comes from one of three places: reusing/slightly varying the previous run's shape, a fresh fully-random shape, or a real motif pulled from a recording of Bill's own ThumbJam playing (about half the time a fresh run is needed), put through one random transformation first (played as-is, inverted, played backwards, lightly mutated, or stretched/compressed) so it's recognizably his phrasing but never repeats exactly — on either synth.
- In the background, it cycles presets on **both** synths, independently of each other, on independent cadences:
  - **Supernova II Performances** — picks one at random, numbers 000–099, plays it for one "song unit" (17 minutes 17 seconds), then randomly picks the next one. Sent on the Supernova's Global MIDI channel, 16, via its own port.
  - **microKORG XL presets** — picks one at random from the full 000–127 range (no exclusions — Bill feeds live audio into the Korg's vocoder input, so even the mic-only vocoder programs produce sound on his rig), plays it for 5 minutes 55 seconds, then randomly picks the next one. Sent via the Korg's own dedicated port, entirely separate from the Supernova's.

  Both start cycling immediately at launch and keep going the whole time the script runs — there's no prompt to answer, they just cycle on their own with independent random picks (no coordination between what the two synths land on, and different dwell times).
- **17:17 as the song unit:** 17 minutes 17 seconds (1037 seconds) is the standard length everything else is measured against — it's how long each Supernova Performance plays before switching, and it's also the base cycle length several slow "modulation" systems breathe on (see below). The Korg's preset dwell (5:55) is intentionally on its own, independent cadence.
- **Modulation systems:** several independent, slow-moving controls run on the computer side. Each one is a smooth, continuously-rising-and-falling curve (no sudden jumps) whose cycle length is a multiple of the 17:17 song unit. Every Supernova Part gets its own copy of the steering modulators below, offset from the other 7; the Korg gets its own copy too, on its own phase, chosen not to line up with any Supernova phase.

  Steering modulators — reshape the ranges the note/run/mod-wheel logic picks from, rather than sending their own MIDI messages. Apply identically to every voice, Supernova and Korg:
  - **Density** (1 song unit) — how close together notes trigger; busier vs. sparser.
  - **Dynamics** (1.5 song units) — an overall loudness swell.
  - **Channel presence** (2 song units) — each channel fades in and out of prominence on its own offset schedule, so the ensemble feels like it's breathing rather than everything swelling together. A channel is always thinned at minimum, never fully silenced.
  - **Mod wheel drift** (0.5 song units) — the center point the mod wheel's random values wander around, per channel.
  - **Run frequency** (0.75 song units) — how often the wandering melodic runs happen; runs come more often during "busy" parts of the arc and less often during "sparse" parts.

  Sound-design modulators — **two separate systems, one per synth, each sent via that synth's own port**, using that synth's own real CC numbers:

  *Korg-only* (its own port) — the microKORG XL's own front-panel knobs. One instance, offset parameter-to-parameter since there's only the one voice:
  - **Pitch drift** (1.25 song units) — a gentle Pitch Bend wobble, roughly ±0.3 semitones assuming the synth's default ±2 semitone bend range.
  - **Hardness** (1.75 song units) — Drive/Wave-Shape Depth, adding or easing off edge/grit.
  - **Filter cutoff** (2.25 song units) — Filter 1's brightness, kept mostly open so patches don't drift into inaudible territory.
  - **Filter resonance** (2.75 song units) — Filter 1's resonance, kept just shy of self-oscillation.
  - **Osc sync** (3.25 song units) — OSC2's mod control. The synth itself divides this knob into four zones (off / ring mod / sync / ring+sync), so this drifts through those modes rather than a smoothly variable "amount of sync" — that's a hardware limitation, not something the script can smooth out.

  *Supernova-only* (its own port, channels 1–8) — the Supernova II's own real MIDI Controller Allocation CCs (from Bill's manual), a completely separate set of CC numbers from the Korg's — the two systems never collide since they're different numbers on different ports. One instance per Part, each on its own channel phase plus its own parameter phase, all 8 spread evenly around the circle. Bill specifically loves how envelope changes here morph the Korg's vocoder output (which is fed by the Supernova's audio), so the envelope drifts are the actual point of this system:
  - **Filter cutoff** (1.1 song units) — never fully closes, floor of 30.
  - **Filter resonance** (1.6 song units)
  - **Filter overdrive** (2.1 song units)
  - **Filter env amount** (2.6 song units) — modest range so the filter envelope stays expressive rather than swinging to extremes.
  - **Amp env attack** (3.1 song units)
  - **Amp env release** (3.6 song units)
  - **Filter env decay** (4.1 song units)
  - **Filter env sustain** (4.6 song units)

## How to run it

1. Make sure `python-rtmidi` and `mido` are installed:
   ```
   pip install python-rtmidi mido
   ```
   (`mido` is only needed for recording — see "Recording" below.)
2. Connect both synths (see MIDI setup below).
3. Run:
   ```
   python3 sn2_chaos8_runs.py
   ```
4. The script opens **two** hardware MIDI ports automatically:
   - The Supernova's own port — it looks for a name containing "korg", "microkorg", "supernova", or "microkey" and connects automatically. If it can't find one, it lists all available MIDI ports and asks you to type the number of the one to use.
   - The Korg's own sound-engine port — it looks for a name containing both "korg" and "sound" (e.g. "microKORG XL SOUND"). If it can't find one, it prints a message and disables the Korg voice for that run rather than falling back to sending Korg data somewhere it won't be heard.
5. It then starts playing immediately, recording as it goes (see "Recording" below), and keeps going until you stop it.
6. To stop: press `q` then Enter, or press `Ctrl+C`. Either way it sends "all notes off", re-centers pitch bend on both synths' ports, and saves the recording before it exits, so nothing gets stuck playing or stuck detuned and the take isn't lost.
7. **This is crash-safe.** If the script gets killed some other way (closing the terminal, `kill`, or even a bug that crashes one of its background threads), it still silences both ports (and saves the recording) before actually exiting — see "Crash-safe shutdown" below. It should not be possible for the script to die and leave a note droning until the machine gets power-cycled.

## MIDI setup

This is a **two-synth, two-port rig** — the Supernova and the Korg are reached over two entirely separate MIDI connections, not one shared cable with different channels:

- **Novation Supernova II** — its own MIDI OUT/DIN port ("MIDI OUT" or "Supernova" in the port list). Gets notes/mod wheel/runs and the filter/envelope sound-design drift on channels 1–8 (one per Part), and Performance changes on its Global MIDI channel, which needs to be set to **16** on the unit itself (Global menu → Global Midi channel). Its factory-default global channel is 1, not 16 — if Performances stop changing, that setting is the first thing to check.
- **Korg microKORG XL** — its own, separate USB-MIDI port for its sound engine (named something like "microKORG XL SOUND" — distinct from any DIN thru port it might also expose). Gets its own notes/mod wheel/runs, preset cycling, and sound-design CC drift there. Bill's rig also feeds live audio into the Korg's vocoder audio-in (mic → audio interface → a second interface output into the Korg), so the vocoder-category factory presets are included in the random cycling rather than skipped — they vocode that incoming audio instead of sitting silent.

If either port can't be found automatically, the Supernova's falls back to a manual pick from the printed port list; the Korg's simply disables that voice for the run rather than guessing. **There is intentionally no path anywhere in this script that reaches the Korg by sending data on some channel of the Supernova's port** — the two are only ever addressed through their own, separate ports.

The Korg sound-design modulators (pitch, hardness, filter, sync) send real MIDI Control Change numbers taken from the microKORG XL's own Owner's Manual (front-panel-knob CC assignments): Filter 1 Cutoff = CC#74, Filter 1 Resonance = CC#71, Drive/Wave-Shape Depth = CC#83, OSC2 Osc Mod (includes Sync) = CC#19. Pitch drift uses a Pitch Bend message rather than a CC, since the synth doesn't expose raw oscillator pitch as a knob/CC. These go out the Korg's own port only.

The Supernova sound-design modulators (filter cutoff/resonance/overdrive, and the envelope attack/release/decay/sustain/amount) send real MIDI Control Change numbers taken from the Supernova II's own MIDI Controller Allocation chart (a completely different set of CC numbers from the Korg's): Filter Cutoff = CC#105, Filter Resonance = CC#106, Filter Overdrive = CC#104, Filter Freq Env 2 Amount = CC#107, Env 1 (Amp) Attack = CC#108, Env 1 (Amp) Release = CC#111, Env 2 (Filter) Decay = CC#115, Env 2 (Filter) Sustain = CC#116. These go out the Supernova's own port, channels 1–8 only.

**MIDI fan-out for the visualizer:** on top of the two hardware ports, the script also opens a third, virtual MIDI port named **`sn2 chaos → visuals`** and sends every single message from EITHER synth — notes, mod wheel, pitch bend, both sound-design systems' CCs, and both synths' preset/Performance changes — out to it too, identically. Launch the butterchurn visualizer with `MIDI=1` (it matches "visuals"/"sn2") and it reads the exact same combined stream in perfect sync, including the channel-16 Program Change used as the clock pulse. If the virtual port can't be created for some reason, the script prints a message and just keeps running against the two hardware ports as before — it won't crash or block on this.

## Recording

Both scripts record every session automatically, via the shared `sn2_recorder.py` helper — no setup needed beyond having `mido` installed.

- **What's captured:** literally everything either script sends — every note, every CC (mod wheel, both sound-design systems), every pitch bend, and both synths' preset/Performance changes — tagged by source: `sn2_ch1`-`sn2_ch8` (a Supernova Part), `sn2_global16` (the Supernova's Performance changes), `korg9` (the Korg). It's hooked at the same `_emit()`/`_emit_korg()` point the MIDI fan-out uses, so nothing that reaches the synths (or the visualizer) can be missed.
- **Where it lands:** `~/Music/sn2-recordings/`, created automatically if it doesn't exist. Each session writes two files, timestamped: `sn2chaos8_YYYYMMDD_HHMMSS.jsonl` / `.mid` (from `sn2_chaos8_runs.py`) or `sn2perpatch_YYYYMMDD_HHMMSS.jsonl` / `.mid` (from `sn2_perpatch_runs.py`) — the prefix tells you which script made it.
- **The `.jsonl` is the real-time safety net:** every message is queued and written to this raw log by a background thread as the session runs, flushed to disk every ~20 events or ~2 seconds of idle time (whichever comes first) — so even an unclean death loses at most a couple of seconds. Recording a message is just a non-blocking queue push in whichever thread is sending it, so it can't add latency to note/CC timing.
- **The `.mid` is generated from the `.jsonl`** as a type-1 (multi-track) Standard MIDI File: one track per source (8 Supernova Parts + Korg + the Supernova's Global/Performance channel — 10 tracks), each named, plus a leading "SN2 Session" conductor track carrying tempo (120 BPM) and time signature (4/4). PPQ 480. The 120 BPM tempo is only used to convert the recorded wall-clock timestamps into ticks — the actual music is free-time, so notation software will show it as rhythmically dense/complex. That's expected; the point is correctly-separated, faithfully-timed data (one instrument per track/staff), not sheet music.
- **When it's finalized:** automatically after `RECORD_DURATION_SECONDS` (2 hours) — the `.jsonl` is closed and rendered into the `.mid`, and the script prints where it saved. The music keeps playing after that; only the recording stops. It's also finalized immediately on any clean shutdown (`q`/Ctrl+C) or crash-safe shutdown (SIGTERM, a background-thread exception) via the same `cleanup()` used for silencing both synths, so a shorter session still yields a usable file. Finalizing is idempotent, so whichever trigger fires first "wins" and the other becomes a harmless no-op.
- **If the process dies before finalize() ever runs** (e.g. `kill -9`, a power cut) the `.jsonl` log still has everything up to its last flush. Regenerate the `.mid` from it directly:
  ```
  python3 sn2_recorder.py ~/Music/sn2-recordings/sn2chaos8_20260821_014353.jsonl
  ```
  This writes the matching `.mid` next to it (same name, `.mid` extension) and tolerates a truncated/corrupt last line, silently skipping it rather than failing the whole regeneration.

## Per-patch runs variant (`sn2_perpatch_runs.py`)

Everything above — routing, presets, modulation, both sound-design CC systems, crash-safety, the fan-out — is identical between the two scripts. The only difference is how "runs" (the wandering melodic phrases) are scheduled:

- **`sn2_chaos8_runs.py`** (main): one global run at a time, cycling between all 9 targets (8 Supernova Parts + Korg), with a long pause (10-45s) between each.
- **`sn2_perpatch_runs.py`** (this variant): **9 independent run streams**, one per Supernova Part plus one for the Korg. Each stream:
  - Fires a run roughly **every 30 seconds** (25-35s, randomized per firing, staggered at startup so all 9 don't fire together).
  - Each run lasts **roughly 4-8 seconds** (randomized per run).
  - Notes within a run land at **randomly-spaced onset times** (0.4-1.2s apart, re-drawn per gap) rather than fixed back-to-back timing — so the note count naturally varies to fill the window (typically 4-10 notes) instead of being locked to the underlying pattern's own length (the pattern's shape just cycles/repeats if more notes are needed).
  - **No global "one run at a time" limit** — a run on Part 3 and a run on the Korg (or any other Part) can be sounding at the same time; that's the whole point, all 8 patches + the Korg trading off and overlapping instead of taking turns.
  - Still uses a per-channel/per-voice lock (`channel_locked` for a Supernova Part, `korg_run_locked` for the Korg) so that specific channel's own background chaos pauses for the duration of *its own* run — unaffected by what any other channel or the Korg is doing.
  - The melodic material is unchanged: reusing/mutating that stream's own last pattern, a fresh random shape, or a ThumbJam motif + transform (same `RUN_THUMBJAM_PROB` chance) — each of the 9 streams tracks its own pattern history independently now, rather than one shared history across a single global run system.

If the ~30s cadence, 4-8s duration, or 0.4-1.2s note spacing feels off once you hear it, those are exactly the numbers to hand back for tuning — `RUN_CADENCE_MIN/MAX`, `RUN_DUR_MIN/MAX`, and `RUN_NOTE_GAP_MIN/MAX` at the top of `sn2_perpatch_runs.py`.

## Crash-safe shutdown

Bill reported the script once crashed and left notes droning on the synth for about 1.5 hours until he power-cycled the machine — that shouldn't be possible anymore. All Notes Off + centered Pitch Bend on **both ports** — the Supernova's channels 1–8 and the Korg's own port — is now guaranteed no matter how the script stops:

- **Ctrl+C or a `kill` command** (SIGINT/SIGTERM) always triggers the full silence-everything sequence before the process actually exits.
- **If the script itself crashes** — an unhandled error anywhere in its background work — the same silencing sequence runs automatically, then the script shuts itself down cleanly, instead of quietly leaving one part broken (and possibly a note stuck) while everything else kept running for hours unnoticed.
- **A single note getting stuck mid-run** is separately guarded against: if something goes wrong between a note starting and its scheduled note-off, the note-off still gets sent immediately rather than left hanging.
- **The recording is also finalized** as part of the same `cleanup()` — the `.jsonl` log is closed and rendered into a `.mid` on any of the paths above, not just a clean `q`/Ctrl+C. Even if that somehow fails, the raw `.jsonl` log itself was already being flushed to disk every ~2 seconds throughout the session, so the take survives regardless (see "Recording" above).

None of this is airtight against every conceivable failure (e.g. the USB-MIDI interface itself dropping out has no software fix), but the specific "process dies and something keeps sounding" scenario Bill hit is now covered from several independent angles, so no single missed case leaves it silent.
